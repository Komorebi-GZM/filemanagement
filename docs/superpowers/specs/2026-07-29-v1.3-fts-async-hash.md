# 本地文件多标记交叉管理系统 V1.3 需求设计文档 (PRD)

## 1. 项目背景

### 1.1 版本回顾

V1.0 完成了核心基础建设：文件导入、SHA256 哈希去重、多级标签树、软删除机制、MVVM 分层架构、图片和文本文件预览。

V1.1 完成了交互范式重构：全局命令面板（Ctrl+K）、智能侧边栏动态计数、右侧 Inspector 面板就地编辑标签，大幅提升了操作效率和数据量级感知。

V1.2 完成了文件系统实时同步：集成 watchdog 实现本地文件监控（创建/修改/删除/移动自动同步），补全了搜索历史写入与命令面板箭头键回溯，消除了路径断裂导致标签失效的核心隐患。

### 1.2 现状与缺口

当前系统存在两个关键缺口：

1. **搜索局限于元数据**：用户只能按文件名、扩展名和标签搜索文件，无法通过文件内容定位目标。当用户忘记文件名、只记得文档里有某句话时，系统无能为力。

2. **SHA256 阻塞主线程**：`sha256_file()` 在 `main_viewmodel.py:299 / 776 / 799` 同步调用执行，导入 500 个以上大文件时 UI 冻结数秒到数十秒。这是 V1.0 延续至今的工程债务，直接影响批量操作体验和 V1.3 FTS 索引流程的可行性。

### 1.3 V1.3 目标

- **P0（首要核心）**：集成 SQLite FTS5 实现文件内容全文搜索，支持 Tier 1-2 文件格式（TXT/MD/LOG/CSV、PDF/DOCX/XLSX）。
- **P0（同等重要）**：将 SHA256 计算异步化到后台线程，消除导入和索引过程中的 UI 阻塞。
- **P1（顺手完成）**：FTS 索引与 V1.2 Watchdog 联动，实现增量更新。
- **P2（明确延后）**：批量操作（批量打标、CSV 导入导出）推迟至 V1.4；PDF OCR 推迟至 V2.0；Tier 3 格式（PPTX/ODT/RTF）为可选项，视开发余量纳入。

## 2. 文件格式支持范围

### Tier 1 — 原生支持（高优先级，必须做）

| 格式 | 提取方式 | 备注 |
|------|----------|------|
| `.txt` | Python 内置 `open().read()` | 需处理编码（UTF-8/GBK/ANSI 自动探测） |
| `.md` | 同 `.txt`，直接读纯文本 | Markdown 语法本身不影响搜索内容 |
| `.log` | 同 `.txt` | 纯文本日志文件 |
| `.csv` | 同 `.txt` | 结构化数据按纯文本索引，不强解析 |

### Tier 2 — 文档格式（高优先级，必须做）

| 格式 | 提取方式 | 依赖库 | 备注 |
|------|----------|--------|------|
| `.pdf`（文本型） | PyMuPDF (fitz) 提取全部文本 | `pymupdf` | 扫描型 PDF 跳过（见下文） |
| `.docx` | python-docx 提取段落 + 表格文本 | `python-docx` | 不处理批注/修订痕迹 |
| `.xlsx` | openpyxl 遍历所有 sheet 单元格 | `openpyxl` | 仅提取文本内容，不处理公式/图表 |

### Tier 3 — 扩展格式（中优先级，可选项，视时间决定）

| 格式 | 提取方式 | 依赖库 |
|------|----------|--------|
| `.pptx` | python-pptx 提取所有 shape 文本 | `python-pptx` |
| `.odt` | odfpy 或 textract | `odfpy` |
| `.rtf` | striprtf 库 | `striprtf` |

### Tier 4 — 明确不做（V1.3）

| 格式 | 原因 |
|------|------|
| `.doc`（旧版 Word） | 需要 antiword/catdoc 二进制依赖，安装复杂 |
| `.xls`（旧版 Excel） | xlrd 提取可靠性不足 |
| 图片 `.jpg/.png/.gif` | 需要 OCR（见下方说明） |
| 音频 `.mp3/.wav` | 超出"文件管理"边界 |
| 视频 `.mp4/.mov` | 超出"文件管理"边界 |
| 压缩包 `.zip/.rar/.7z` | 需解压，性能和安全风险高 |
| 加密/带密码文件 | 无法读取，略过 |

### PDF OCR 决策：V1.3 不做

- 本地 OCR（Tesseract）太重：打包体积增加 200-300MB，跨平台安装路径差异大
- 性能问题：单页扫描 PDF OCR 耗时 1-3 秒，百页文档阻塞索引流程
- 准确性不可控：中文/英文混合、低分辨率扫描件识别率低
- 替代方案：V1.3 对扫描型 PDF 跳过索引，但通过 PyMuPDF 检测页面文本长度后，在 UI 标注"该 PDF 为扫描件，无文本可搜"
- 预留接口：`extract_pdf_text()` 函数内部保留 `ocr=True` 参数位，未来可插拔替换

### 3.3 数据流：文件导入全文索引

```
用户导入文件 (import_files)
    │
    ▼ (同步)
sha256_file() + DB upsert
    │
    ▼ (异步: 推入后台队列)
IndexWorker (QThread)
    │  detect format → extract text → upsert FTS
    │  emit indexing_progress(file_id)
    │
    ▼
file_fts 虚拟表 (FTS5)
```

### 3.4 数据流：搜索

```
用户输入搜索词 (CommandPalette / search box)
    │
    ▼
MainViewModel.search_files(query)
    │
    ├── FTS 主查询 (文件名列 + 内容列 同时匹配)
    │       SELECT f.id, f.file_name, f.full_path, ..., rank
    │       FROM file_fts fts
    │       JOIN files f ON f.id = fts.file_id
    │       WHERE file_fts MATCH ?
    │       ORDER BY rank     ← BM25 排序，文件名匹配者自然靠前
    │
    ├── LIKE 辅助查询 (仅当 FTS 返回不足 limit 或查询含中缀通配符)
    │       SELECT ... FROM files WHERE file_name LIKE ? AND id NOT IN (↑FTS结果)
    │       ORDER BY file_name ASC
    │
    └── 合并结果集: FTS 结果 (已按 BM25 排序) + LIKE 补充分贝 (按文件名排序)
    │   → 取前 limit 条
    │
    ▼
    return list[FileRecord]
```

> **排序规则决策**：搜索主通道为单次 FTS 查询，`content` 字段包含 `file_name + " " + extracted_text`（详见 §6.1），因此文件名匹配的文件天然获得更高 BM25 分数。FTS 结果排在前面，LIKE 补充分贝（处理 FTS 无法覆盖的中缀模式，如 `udget` 匹配 `budget`）追加在后。不需要人工设计"文件名精确 > 文件名模糊 > 内容"排序——FTS 的 BM25 自然实现了这一效果。

### 3.5 数据流：Watchdog 联动增量更新

```
文件修改事件 (file_modified / file_created)
    │
    ▼
FileMonitor._flush()  →  file_system_changed 信号
    │
    ▼
MainViewModel._on_file_system_changed(batch)
    │
    ├── 已有逻辑: 更新 files 表 (路径/大小/软删除)
    │
    └── 新增逻辑: 如果文件扩展名在 FTS 支持列表中
                    → 推入 IndexWorker 队列
                    → 重新提取文本 → 更新 file_fts
```

### 3.6 SHA256 异步化

```
现状: import_files 中同步调用 sha256_file(path)
      → UI 阻塞直到所有文件的哈希计算完毕

改造后:
    1. import_files 接收文件列表后立即返回
    2. 后台 ImportWorker (QThread) 逐个计算 SHA256 + DB upsert
    3. 每个文件完成后发射 progress 信号
    4. 界面显示进度条，不冻结
```

## 6. 数据结构变更

### 6.1 FTS5 虚拟表（新增）

```sql
-- 全文搜索虚拟表
-- content 字段存储 "file_name + " " + extracted_text"
-- 这样文件名和内容通过一次 FTS 查询即可覆盖，BM25 排序
-- 自然让文件名匹配的结果排在前面（文件名短、词频集中）
CREATE VIRTUAL TABLE IF NOT EXISTS file_fts USING fts5(
    file_id UNINDEXED,
    content,
    tokenize='unicode61'
);

-- 注意：FTS5 是 SQLite 虚拟表，不能使用普通 CREATE INDEX
-- 对 file_id 的查询通过外部 files 表关联
-- FTS5 内置隐藏列 rank（BM25 分数），ORDER BY rank 即可获得相关性排序
```

> **upsert_fts 约定**：调用者传入 `(file_id, file_name, extracted_text)`，由 `upsert_fts` 拼接后写入 `content` 字段。拼接格式：`f"{file_name} {extracted_text}"`。文件名在前确保 BM25 排序中文件名权重高于正文。

### 6.2 file_content_status 表（新增）

```sql
-- 记录每个文件的索引状态
-- 任何时候都不应存在"僵尸 pending"记录
CREATE TABLE IF NOT EXISTS file_content_status (
    file_id INTEGER PRIMARY KEY,
    content_length INTEGER NOT NULL DEFAULT 0,
    status TEXT NOT NULL DEFAULT 'pending',
        -- 'pending' | 'indexed' | 'skipped_too_large' | 'skipped_format' | 'error'
    error_message TEXT,
    indexed_at INTEGER,
    FOREIGN KEY (file_id) REFERENCES files(id) ON DELETE CASCADE
);
```

> **状态转换约束**：`pending` 仅为初始化默认值。`IndexWorker` 处理完每个文件后（无论成功/跳过/错误）**必须**立即将状态更新为对应值，不允许 `pending` 记录遗留。`pending` 只会在初次启动扫描时短暂存在。如果在索引过程中发现已有非 `pending` 记录，说明该文件已被处理过，应跳过（避免重复索引）。

## 7. 技术选型

### 7.1 FTS5 分词器

使用 `unicode61` 分词器，支持中文、英文、数字混合搜索。`unicode61` 是 SQLite 内置分词器，无需额外编译。

```sql
CREATE VIRTUAL TABLE file_fts USING fts5(
    file_id UNINDEXED,
    content,
    tokenize='unicode61'
);
```

搜索语法：
- `MATCH ?` 使用 `?` 占位符传参（避免 SQL 注入）
- 默认支持 `AND` / `OR` / `NOT` 逻辑操作符
- 支持短语搜索（双引号包裹）
- 前缀搜索（`word*`）

### 7.2 文本提取超时控制

```python
from concurrent.futures import ThreadPoolExecutor, TimeoutError

def extract_text_with_timeout(path: Path, file_ext: str, timeout: float = 5.0) -> str:
    with ThreadPoolExecutor(max_workers=1) as executor:
        future = executor.submit(extract_text, path, file_ext)
        try:
            return future.result(timeout=timeout)
        except TimeoutError:
            logger.warning("Text extraction timed out: %s", path)
            return ""
```

### 7.3 SHA256 异步化方案

使用 `QThread` + `pyqtSignal` 模式，与 V1.2 的 `FileMonitor` 保持一致的线程策略：

```python
class ImportWorker(QObject):
    progress = pyqtSignal(int, int, str)  # current, total, file_name
    finished = pyqtSignal(int)            # total_inserted

    def __init__(self, candidates: list[ImportCandidate], db: Database):
        super().__init__()
        self._candidates = candidates
        self._db = db

    def run(self):
        inserted = 0
        for i, c in enumerate(self._candidates):
            file_hash = sha256_file(c.path)
            # ... DB upsert (与现有逻辑相同) ...
            self.progress.emit(i + 1, len(self._candidates), c.path.name)
            # 注意：DB 连接在后台线程中使用，需使用独立连接
        self.finished.emit(inserted)
```

## 10. 风险评估

| 风险 | 可能性 | 影响 | 应对策略 |
|------|--------|------|----------|
| PyMuPDF 在某些 PDF 上提取乱码 | 中 | 低 | 使用 `try/except` 保护，提取失败时标记为 error 并记录日志，不影响其他文件 |
| python-docx 遇到损坏的 .docx 文件崩溃 | 中 | 低 | 使用 try/except 包裹提取逻辑；损坏文件标记为 error 并跳过 |
| FTS5 在 SQLite 旧版本不可用 | 低 | 高 | Python 3.11 内置的 SQLite 版本（3.40+）已支持 FTS5；验证方法：`PRAGMA compile_options` 检查 ENABLE_FTS5 |
| 异步导入导致数据库并发访问冲突 | 中 | 中 | 后台线程使用独立数据库连接；通过队列串行化写入，不并发 |
| 大量小文件（10000+）同时进入索引队列 | 中 | 中 | IndexWorker 设置队列上限（默认 10000），超出时丢弃最早未处理项 |
| chardet 对大文件编码探测缓慢 | 低 | 低 | 限制 chardet 检测的输入大小（前 10KB 即可准确判断大部分编码） |
| 用户搜索 FTS 导致性能下降 | 低 | 中 | FTS5 索引搜索通常比 LIKE 快 10-100 倍；在搜索历史中增加搜索耗时统计可辅助诊断 |
| 渐进式索引时用户搜索刚索引完的文件但 FTS 尚未更新 | 中 | 低 | 搜索主流程为 FTS + LIKE 双通道，即使 FTS 暂缺也不丢失结果（LIKE 兜底） |
| 增量索引队列积压（Watchdog 高频事件 + 初次索引未完成） | 中 | 低 | IndexWorker 队列上限 10000；超出时丢弃最早未处理项，最新文件优先 |

## 11. 向下兼容说明

- **数据库 Schema**：追加 FTS5 虚拟表和 `file_content_status` 表，原有表完全不变。V1.2 数据库可直接升级。
- **已有文件**：用户升级后，后台自动为已有文件建立索引。

  **渐进式索引策略**：
  - 触发时机：V1.3 首次启动时，扫描 `files` 表中 `file_content_status` 不存在或状态为 `pending` 的所有记录（即尚未索引的文件）。
  - 批次大小：每批 100 个文件。批处理是异步的，不阻塞 UI 线程。
  - 节奏：每批完成后暂停 200ms（避免 CPU 100%），然后继续下一批。
  - 顺序：优先索引最近修改（`modify_time DESC`）的文件，让用户最新使用的文件最快可搜。
  - UI 反馈：右下角状态栏显示 `正在构建内容索引... 128/5430`，点击可查看详情。索引完成后自动消失。
  - 中断/恢复：用户关闭应用时，正在处理的批次进度保存在 `file_content_status` 表中。下次启动时从中断处继续。
  - 退出策略：所有文件处理完后，`indexing_finished` 信号触发状态栏提示消失。后续仅通过 Watchdog 增量更新。
- **搜索接口**：`search_files()` 返回值不变（仍为 `list[FileRecord]`），新增 FTS 搜索作为内部扩展。
- **UI 布局**：不改变主窗口布局。搜索结果列表在搜索内容时自动展示内容匹配结果。
- **打包配置**：`filemanagement.spec` 需确认 PyInstaller 正确收集新依赖（pymupdf, python-docx, openpyxl, chardet）。
